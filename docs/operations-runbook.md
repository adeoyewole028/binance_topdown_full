## Ownership, topology and limits

One Linux service instance owns one persistent disk, transactional SQLite and exactly one execution/scanning process. `run_supervised.py` starts one `run_worker.py --scan --operations` and two passive Gunicorn HTTP workers. Automation remains disabled unless explicitly configured. HTTP imports never start scanners. Kernel fencing and recovering generations remain mandatory on every restart.

The Render blueprint is a reviewable candidate, not an approved purchase: `1c-2g`, one disk and one instance. The 1GB disk entry is a placeholder inherited from the original blueprint, not a capacity acceptance result. Seven days at870-second cadence creates up to696 full snapshots. Before activation measure the full journal/cache snapshot under expected universe and trading load, project growth, and approve sufficient disk/budget for live state plus all retained snapshots and failed-attempt headroom. Do not activate a capacity plan solely from small offline fixtures. No disk can be shared between separately deployed Render web/worker services. Disk services have deployment downtime.

`/healthz` is anonymous, minimal, uncached **recovery-service routing health**, not trading permission. It requires verified store, a matching live supervised owner and recent verified backup. Owner progress expires at the approved600s scanner-health bound; Linux PID death and supervisor child exit are detected separately. Fifteen seconds is monitor/reconciliation cadence. `/api/operational-health` is authenticated and distinguishes control, market and entry readiness. Canonical reviewed-order admission remains authoritative, including per-symbol sizing/caps/cooldown/price freshness. A healthy control plane must remain available during reconciliation, missing setup, entry pause and unknown provider outcomes.

## Secrets, least privilege and rotation

Configure secrets using the host's protected environment store. The configured operator owns incidents. Require a unique session secret, configured operator and password hash. Keep the data directory mode0700 and process umask0077. Restrict shell/disk/backup access to the service owner; encrypt off-host backups and approve their destination and access. Public logs and release artifacts contain allowlisted condition codes, operation/group IDs, configuration version and profile only. No balances, raw provider messages, credential values, raw environment contents or destination URLs are logged.

Provider keys must be venue-specific, trading-only and without withdrawal permission; verify their restrictions at BT15. Rotating an operator hash or session secret revokes existing sessions. To rotate provider access: stop new entries, preserve native protection, stop the owner, change only the reviewed venue's secret, restart under recovering ownership and reconcile identity/orders/fills/balances/protection before entry admission. Key rotation is an external provider gate, not a reason to manufacture an empty account.

Alerts are generic JSON POSTs to the configured private HTTPS webhook, disabled until `OPERATOR_ALERT_DELIVERY_AUTHORIZED=true` is explicitly authorized. Redirects are refused. Confirm the receiver supports the payload/event-ID contract before activation; setting a URL does not prove delivery. Keep the URL secret in host configuration. Delivery failure logs only an event ID and retries retain event identity. Pending incidents survive later condition changes; acknowledged receipts move to the private delivered archive. Delivery is at least once: a lost acknowledgement can cause the same event ID to arrive again, so the receiver must deduplicate that ID. Each monitor tick attempts at most one delivery, prioritizing the current incident before retained backlog. Changing the configured receiver requeues the current incident without replaying acknowledged historical incidents. A dead host cannot send its own alarm: configure and prove an independent approved host/provider availability alarm before activation.

## Incident actions

- **Unknown outcome / account mismatch:** stop new entries through the approved exchange entry control. Find the durable operation by its ID/token; reconcile the original provider client identity. Do not create a replacement order, reset account state or interpret an HTTP success as a fill. Confirm actual fills, fees and balances; unresolved states remain blocked.
- **Unprotected exposure:** stop new entries, preserve existing confirmed fills and surviving native legs. Reconcile list and both leg identities, then use reviewed risk-reduction/reprotection only when safe. An unknown cancellation cannot permit a second sell. No automatic emergency liquidation or invented trailing policy.
- **Scanner/data/access incident:** inspect authenticated operational health, budget block and last completed scan. Prices expire60s; scan health expires600s. The explicit owner refreshes prices30s and schedules reconciliation15s. A failed refresh never advances freshness. Review access failures before the existing stopped-owner `resume-market` command; do not bypass provider budget/auth gates.
- **Owner loss/restart:** supervisor stops the peer process and exits. Restart acquires a new kernel-fenced recovering generation; unresolved order/protection effects are reconciled by original identity. There is no blind retry. Retain journal and provider protection during process termination.
- **Disk full/corruption/backup failure:** stop service intake/owner, retain live and incomplete artifacts, preserve exchange-native protection. Never delete financial history, auto-create an empty store or restore over newer effects. If alert persistence is unavailable, use the independent host alarm and sanitized service logs. Expand storage only after capacity/budget approval; then reconcile before new entries.

## Backup, restore and recovery objectives

Approved targets: retain7days, RPO900s, RTO3600s. The supervisor schedules full consistent SQLite backups at870s with15s observation cadence, independently of slow market scans. Each snapshot verifies database integrity, foreign keys, store identity, schema1 and journal sequence, then fsyncs and atomically publishes. Publication updates a private verified-backup health marker. Worker maintenance refuses execution if that marker is missing, foreign, from the future or900s old. Never describe an incomplete attempt as a backup.

Retention removes only the four verified manager-owned files in expired same-store snapshot directories. Unrelated directories, symlinks and incomplete attempts are retained or refused. Do not recursively delete arbitrary data paths. Monitor disk headroom and incomplete failures; the approved policy does not permit destructive journal cleanup.

Same-disk snapshots cover process/accidental-state recovery; they do **not** establish host/disk-loss RPO. Configure, authorize and test an independent encrypted copy/retrieval of complete snapshots within the same900s objective before activation. No external upload or storage provider is configured by this ticket's local work. Under realistic journal size/load measure backup completion time, off-host availability, retention capacity and restoration; small local drills do not establish production RPO/RTO.

For restore: stop all writers; preserve the current journal; select the complete verified same-store snapshot; `python manage_state.py restore-candidate BACKUP NEW_ISOLATED_DIRECTORY`. Restore refuses checksum/identity/schema/sequence inconsistencies and refuses to discard newer committed effects. Inspect the candidate through the ordinary authenticated application and prove operations/fills/balances/holdings/protection provenance. Recover any post-backup provider effects through reconciliation before cutover. Cutover to a reviewed candidate is a separately authorized operation; never overwrite the original store. Record measured time and restored sequence. Rotate sessions if needed; fresh authentication state does not create financial capital.

## Upgrade, release and rollback

There is one source release path: manually dispatched **Verified release** workflow on main, after all checks for the exact revision pass and protected `production` environment approval. Push/PR events validate only. Platform `autoDeployTrigger` must beoff; retire existing deploy hooks and competing triggers only through authorized provider configuration. Configure the approved service ID, plan and health URL as protected environment variables, and API key as a protected secret. Missing configuration fails rather than silently skipping a release.

Before dispatch record a current verified backup, store/migration compatibility, capacity/budget, tested Linux runtime, operator/alert/off-host recovery evidence and a compatible rollback revision. The release command verifies service identity, paid approved plan, one instance/no autoscaling, persistent mount, no competing deploy, and health URL bound to that service before submitting **one** exact commitId. It checks provider deployment state/revision and minimal control readiness; this does not prove authenticated trading or live provider acceptance. Unknown deployment response requires inspecting the existing deployment before another dispatch.

During upgrade stop new entries; preserve native stops and pending operation identities. Let the supervisor terminate the owner/HTTP processes without canceling protection; journal any in-flight ambiguity through normal recovery. Apply only reviewed explicit additive migration on the mounted disk. The restarted supervisor validates state/backup before children run. Reconcile and verify authenticated recovery/settings/history journeys after deployment; retain mode/venue isolation and disabled automation unless separately authorized.

Rollback triggers: failed readiness, incompatible state, owner competition, missing provenance, new unknown/unprotected exposure, failed recovery, stale execution data or unavailable observability. Stop new entries first. Dispatch the same release workflow only for a previously verified compatible revision with current journal retained. Never restore an older financial database or deploy pre-remediation JSON writers. If no compatible rollback package exists, remain stopped and reconcile; do not invent a rollback target. Record revision/environment, actual provider and browser acceptance, monitoring interval and unresolved limitations. Deployment, activation and BT15/BT16 acceptance are separate milestones.
