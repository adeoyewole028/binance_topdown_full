# Durable state and quarantined migration (BT03)

BT04 adds completed-bar/freshness guards and a versioned additive request-budget extension. See [market-data operations and explicit upgrade](market-data.md). Existing BT03 initialization/backup guarantees remain; no numerical D07 target is pending now, and its actual backup/supervisor implementation remains BT14.

The approved topology is one host, private local disk, transactional SQLite, and one supervised execution owner per local account/venue across paper/exchange modes. HTTP processes never submit provider orders. `DATA_DIR` must be identical for every process; use a private OS account and permissions, never independent disks, replicas or network filesystems. `LOCAL_ACCOUNT_ID` is an opaque configured identifier, not a provider credential. Venue and mode qualify every financial row; HTTP input cannot select another namespace.

`trading.sqlite3` is authoritative. `state-identity.json` independently binds its identity/schema. Opening missing, mismatched or corrupt state fails closed and never initializes an empty account. All durable monetary/crypto values are decimal strings. Config versions, fills, provider observations, balance movements and journal events are append-only. Intent intake, its config reference and journal sequence commit together; paper fills, positions and journal effects commit together. Schema v1 includes protection, reservations, cooldown and observation identities for their later lifecycle tickets; those behaviors are not activated by BT03.

The lifetime kernel lock is held by `run_worker.py` or the owned scanner. No TTL or stale heartbeat grants ownership. A new holder increments its generation and starts recovering; unresolved dispatch/unknown/processing/canceling operations block new dispatch. Loss of DB identity or ownership confirmation stops the owner. Exchange mode submits no orders until BT06 implements reconciliation. The interim `legacy-paper-v1` projection preserves valid manual quantities but has unknown capital and fees; it is not the credible BT05 simulator. Old standalone daemon execution is retired pending BT09. Scanner freshness, supervision SLOs and admission rules remain BT04 work.

## Explicit local initialization and migration

These commands are instructions for an authorized maintenance window; this change has not run them against existing account files. Stop all old/new HTTP writers, scanners, daemon and owner first. Save the old binaries and sources for inspection, but never resume an old JSON writer after cutover.

1. Configure the environment, operator and a private `DATA_DIR`. `python manage_state.py init` explicitly creates fresh schema or an additional isolated namespace. If either required DB/identity already exists but is invalid, initialization refuses repair. Never delete required state to make initialization succeed.
2. `python manage_state.py quarantine <positions.json> <config.json> <trades.csv>` copies exact bytes into checksum-qualified read-only backups, then records quarantine transactionally. Source files become read-only migration inputs. Inspect output counts/checksums; repeat quarantine/import produces no additional effects. Config/CSV stay review-only, and their arbitrary fields do not enter runtime state. Configure approved settings explicitly; CSV is not complete fill/capital history.
3. All snapshots remain quarantined until their paper origin is confirmed. For each reviewed positions checksum, use `python manage_state.py confirm-paper <checksum> --actor <operator-id> --confirmation paper:<namespace>:<checksum>`. The attestation binds this exact namespace and file. It imports finite positive quantities/entries once, quarantines duplicate symbols/invalid rows/overlapping existing positions, and reports imported/quarantine counts. It journals an opening provenance event, never fabricated fills, fees or initial capital. Inspect the quantities through authenticated `/api/status`; compare with the source manifest. Unknown origin cannot become exchange holdings. Exchange holdings always require BT06 provider reconciliation.
4. `python manage_state.py inspect` checks integrity and exposes redacted identities/counts/ownership. Acquire the owner only after review. Local paper uses `python run_worker.py --scan` (advisory scanner and queued paper projection), or `python run_worker.py --once` for a controlled consumer step. The scan loop snapshots one config version. Actual automation is disabled. Production supervisor/release installation and activation require later gates.

## Backup, restore and rollback

`python manage_state.py backup <new-directory>` uses SQLite's online backup API to create a consistent whole-store snapshot, then records its checksum, identity and journal high-water sequence. It does not copy a live DB file while ignoring its journal. An incomplete backup without a valid manifest is unusable. Retain backup directories under private permissions. Schedules, retention, RPO/RTO and deployed restore exercises are BT14/D07 gates.

`python manage_state.py restore-candidate <backup-directory> <new-directory>` verifies the checksum/identity/integrity and prepares a separate candidate. It never overwrites the authoritative DB. If the current store has newer journal effects, restoration refuses; preserve the current store and use a compatible reader or a newer backup. Missing/corrupt required current state also fails closed for review; do not silently erase its identity or pretend the last backup proves that no newer effects existed. An isolated candidate with no current state can be inspected using the same approved account/venue/mode configuration, but this is not automatic recovery authorization.

During an approved service cutover, stop **all** writers, recheck the latest journal, verify candidate contents, keep the current store and quarantine inputs, and use only schema-compatible binaries. Never deploy old JSON-writing binaries onto migrated state. The newer journal stays authoritative on rollback. External provider effects require reconciliation before resuming exchange work; offline backup tests cannot prove them.
