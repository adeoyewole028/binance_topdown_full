# Reviewed manual orders and recovery

Sign in to the operator dashboard, supply the explicit policy, and wait for fresh supervised market data and account reconciliation. Enter a symbol, side and quantity, or choose configured fixed/risk allocation. **Review order** performs no financial write. It shows the server quantity, available funding asset, estimated exposure, estimated execution price and fee, venue/mode, settings/profile version, observed price and existing protection. Estimates do not establish execution.

**Confirm reviewed intent** signs no provider request in the web process. It submits the reviewed intent to the existing transactional queue. The supervised owner applies its authoritative admission, reservation, execution, protection and reconciliation checks. Changes to the request, settings, prices, balances, holdings, protection or owner context require a fresh review. Fresh price and verified market/protection rules are required. Reductions still require a confirmed holding and fresh reconciliation; failed protection does not become an automatic liquidation.

The browser retains the draft, review receipt and intake token in namespace-scoped session storage before confirmation. Refresh, a lost response or a sign-in interruption retains that identity. Browser storage must be available before confirmation. Repeated confirmation returns the same saved operation, including after prices change. **Check recovery status** reads committed operation/fill/protection state; the supervised worker performs provider reconciliation. It does not place or repeat a provider order. When a response is lost, the retained intake token can find the saved operation even without a returned operation ID.

Queued, accepted, unknown and partly filled intents are distinct from confirmed fills. Only recorded fills establish executed quantity, cost and native fee assets. Pending and uncertain outcomes retain their identity and do not offer a replacement order. Protection failure preserves actual fills and holdings, blocks new entries and explains reconciliation. A confirmed terminal operation permits a separate reviewed reduction; the owner still cancels and reconciles existing protective legs before selling. Unknown cancellation cannot authorize another sell. Partial closes use confirmed remaining holdings and protection.

Every current position has **Review close**, independently of exit signals. It loads a sell/close draft; edit the quantity for a partial close or choose **Full confirmed holding**. Neither the button nor loading the draft places an order. Quarantined legacy snapshots remain read-only and are excluded from these current holdings.

HTTP contracts: authenticated CSRF-protected `POST /orders/review` returns a signed review receipt; `POST /orders/confirm` returns 202 with a durable operation, not a fill claim. `GET /api/operations/<id>` and `GET /api/order-token/<token>` are scoped to the authenticated current namespace. Review conflicts are 409, invalid values 422, permission failures 401/403 and unavailable durable state 503. Legacy `/trade` and `/close` remain compatibility adapters to the same owned intake service. They are not dashboard one-click controls.

Scope: offline local acceptance with fake providers is separate from real provider, deployed, native device and assistive technology acceptance. This change does not activate automation or exchange execution, move legacy data, fund an account or deploy a service.
