# Explicit automation through the shared owner

Automation is disabled by default. Setting `AUTOMATION_ENABLED=true` alone does not start it: the operator must explicitly launch `python run_worker.py --automate --sizing risk` (or `--sizing fixed`). Advisory scanning remains `python run_worker.py --scan`; queue-only processing remains `python run_worker.py`, optionally `--once`. Scanning/automation cannot use `--once`.

Before any automated trade, initialize the durable account/venue/mode, complete the explicit operator capital/risk setup, review the stored strategy profile and version, and satisfy the server's existing execution allow gates. Paper setup never happens implicitly. Exchange mode requires matching venue credentials and exchange allow policy; mainnet additionally requires its separately reviewed allow gate. Deployment, provider certification and controlled activation remain separate BT14/BT15 gates. These instructions describe available source behavior and do not activate a service.

The operator's durable settings select `dashboard_intraday` v1 (4h/1h/15m) or `daemon_daily` v1 (1d/4h/15m). No launcher silently changes the selected profile. To preserve the former daemon's daily workflow, explicitly select `daemon_daily` in settings before launching. Both share the documented [strategy definitions](strategy-profiles.md); fixed sizing uses the setup's configured quote currency/allocation, while risk sizing uses confirmed capital and the approved stop/risk bounds. Whitelist/blacklist environment settings constrain entries; existing holdings stay covered for reconciliation and exits.

`python topdown_daemon.py --sizing risk` is a compatibility launcher for the same explicitly gated owned automation. The old `Broker`, CSV/in-memory positions, direct order calls, independent TP/SL orders and monotonic position counter are retired. Integrations importing `Broker` must upgrade to the shared intent/owned-worker interfaces. Legacy snapshots retain the existing quarantine/migration requirements.

One kernel-held owner per account/venue acquires fencing before transport construction. Automation waits for startup reconciliation, complete/current public market data and explicit controls. Completed-bar signal identity includes namespace, venue, profile/version, immutable configuration version, symbol and execution close. Entries use stable journal idempotency keys; repeated scans/restarts cannot create a second intent for one identity, even after that entry has closed. A rejected intent is not silently retried with a new identity. Fresh completed bars can produce fresh signals, still subject to persisted cooldowns, reservations, capital, exposure and position limits.

Automatic exits use the position's entry-bound evaluator/configuration and a fresh close review of its confirmed quantity. Exit intents retain both signal provenance and current dispatch review. Entry pauses/drawdown stops permit reductions; unsupported/unknown protection or ambiguous order outcomes preserve holdings/risk and block entries. Every effect follows the manual executor's reconciliation and [protection](position-protection.md) contracts. No emergency liquidation or trailing contract is added.

Observe `/api/status`: `automation` reports disabled, waiting_for_reconciliation, running, blocked (with reason), or stopped, plus owner generation/sizing and latest signal/operation where relevant. Operations expose manual/automation source and immutable signal provenance. Filled positions, active protection, available/reserved funds and cooldowns are durable projections, not daemon counters. A stopped/replaced owner overrides a stale running journal status; market health must also be consulted after abrupt process death until a supervised replacement reconciles. An HTTP reset or import does not start automation.

SIGINT/SIGTERM stop intake, persist stopped status and release ownership. A stop requested during public scanning prevents subsequent automatic intake in that scan. Accepted/unknown operations remain for recovery, and confirmed native/simulated protection remains intact. A status-write failure propagates instead of claiming success; ownership cleanup still runs, and a replacement must reconcile. Do not delete unknown operations or restart a competing daemon to bypass a blocked status. Recovery uses the existing durable IDs and provider status checks; it does not resubmit a new order blindly.

BT09 validation is offline with disposable state and fake providers. It proves shared entry/fill/protection/exit, restart identity/cooldown/slots, operator gates, actual process fencing and graceful/fault shutdown. Actual provider, deployment, browser/device and controlled trading acceptance are tracked separately.
